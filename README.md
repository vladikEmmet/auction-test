# SPA грузовых аукционов

Тестовое задание: SPA для работы с грузовыми аукционами по OpenAPI-схеме
`openapi/openapi.auctions.v0.json`. Бэкенда нет — его роль играет MSW со стейтом,
который реально меняется после мутаций.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173
```

Другие команды:

```bash
npm run test       # vitest, 266 тестов
npm run typecheck  # tsc --noEmit
npm run lint       # eslint, включая проверку границ слоёв FSD
npm run build      # production-сборка
npm run preview    # просмотр собранной версии
```

Требуется Node 20.19+ / 22.12+. Дополнительной настройки не нужно: MSW стартует из
`src/main.tsx` до первого рендера, данные генерируются детерминированным сидом
(~57 аукционов) и сбрасываются при перезагрузке страницы.

## Демо

Сборка публикуется на GitHub Pages автоматически: workflow `.github/workflows/deploy.yml`
на каждый пуш в `main` прогоняет типы, линт и тесты, собирает проект и выкладывает его.
Pages включаются самим workflow (`configure-pages` с `enablement: true`), отдельных
действий в настройках не требуется. Адрес будет вида
`https://<пользователь>.github.io/<репозиторий>/`.

Если репозиторий приватный на бесплатном тарифе, Pages недоступны — тогда либо сделайте
репозиторий публичным, либо соберите локально и выложите папку `dist` на Netlify Drop.

Приложение умеет жить в подпапке: базовый путь приходит из `VITE_BASE_PATH`, от него же
считаются basepath роутера и адрес service worker'а MSW. Локальная проверка такой сборки:

```bash
VITE_BASE_PATH=/имя-репозитория/ npm run build
cp dist/index.html dist/404.html   # SPA-фоллбэк для прямых ссылок
```

## Стек

React 19, TypeScript (strict), Vite 8, TanStack Router, TanStack Query v5,
React Hook Form + Zod v4, MSW 2, Zustand, Tailwind CSS v4 + компоненты на Radix
в стиле shadcn/ui, Vitest + Testing Library.

## Архитектура

Feature-Sliced Design; границы слоёв проверяет ESLint (`eslint.config.js` собирает
правила `no-restricted-imports` по фактическим слайсам в `src/`).

```
openapi/openapi.auctions.v0.json   схема — источник правды, читается contract-тестом
src/
  app/        провайдеры, роутер (ленивые страницы), стили
  pages/      auctions-list | auction-detail | auction-bet
  widgets/    auctions-filters | auction-card | auction-summary | bets-table
  features/   filter-auctions | set-bet | vat-display
  entities/   auction (queryOptions, VM-мапперы, бейджи статусов), bet
  shared/     ui, lib, api (contracts, http-client, msw), config
  testing/    рендер приложения в памяти и бутстрап MSW для интеграционных тестов
```

Мок-база разложена по обязанностям: `msw/db.ts` — состояние, `projections.ts` — сборка
списочного DTO из детального, `queries.ts` — фильтры и пагинация, `mutations.ts` — ставка,
`ranking.ts` — пересчёт мест (общий для сида и мутаций), `vat.ts` — арифметика НДС;
`store.ts` остаётся публичным API этой шестёрки. Генератор данных — отдельная папка
`msw/seed/`: `lib` (детерминированный PRNG и форматирование дат), `edge-cases`
(декларации особых случаев), `builders` (точки маршрута и ставки), `index` (сборка записи).

Файлы React-компонентов названы с суффиксом `*.component.tsx` — требование задания.

### Ключевые решения

**Контракты.** DTO описаны Zod-схемами в `src/shared/api/contracts`, типы выводятся
через `z.infer`. Соответствие схеме проверяет `contracts.contract.test.ts`: он читает
`openapi.auctions.v0.json` и сверяет набор полей каждого DTO, значения всех enum'ов и
nullable-поля (95 проверок). Расхождение схемы и кода падает тестом, а не в рантайме.
В dev-режиме ответы дополнительно прогоняются через `safeParse`: несоответствие пишется
в консоль как warning, но не роняет экран.

**Правила ставки — один источник правды.** `src/shared/lib/bet-rules.ts` содержит
чистые `getBetConstraints` / `validateBetPrice` / `suggestBetPrice`. Их использует и
форма на клиенте, и MSW-хендлер в роли сервера, поэтому 422 воспроизводим и согласован
с клиентской валидацией. Направление торгов: `Down` — только ниже доступной цены,
`Up` — только выше, `FixPrice` — ровно доступная, `Request` — любая > 0 в границах
min/max. Деньги сравниваются в копейках, чтобы не ловить ошибки float.

**MSW как настоящий стейт.** `store.ts` хранит записи, где источник правды — детальный
DTO, а элемент списка строится проекцией `toListItem`. Поэтому после ставки список,
деталка и история ставок не могут разойтись. `POST /bets` добавляет ставку,
пересчитывает места (рейтинг — по лучшей ставке каждой организации), двигает
`price.current` / `current_no_vat` / `available` / `price_per_km`, обновляет
`your.bet` / `last_bet` и переводит торговый статус в `Leading` или `Losing`.

**Панель фильтров.** В начале страницы форма развёрнута целиком — всё видно сразу.
Ниже идёт строка со сортировкой, размером страницы и чипсами активных условий; при
прокрутке она прилипает под шапкой и получает кнопку «Фильтры» со счётчиком, которая
открывает ту же форму в выезжающей панели (Radix Dialog: снизу на мобильных, справа на
desktop). Пока развёрнутая панель на экране, кнопка скрыта — дублировать нечего;
момент ухода панели из вида ловит `IntersectionObserver` (хук `useOutOfView`).
Поля формы описаны один раз в `FiltersForm`, обёртки различаются только раскладкой.
Открытием выезжающей панели управляет Zustand-стор — это и есть тот «точечный клиентский
UI-state», которого требует ТЗ.

**Search params.** Схема в `features/filter-auctions/model/search-params.ts` навешивает
`.catch()` на каждое поле: `?page=abc&per_page=999&sort=неизвестно&statuses=НЛО`
превращается в дефолты, страница не белеет. `buildListRequest` — чистая функция:
переводит статусы аукциона в числовые коды (API ждёт 1–8), разворачивает даты
`YYYY-MM-DD` в ISO 8601 со смещением (`from` — начало дня, `to` — конец) и не отправляет
незаданные фильтры.

**Первый кадр.** Приложение монтируется только после старта MSW (иначе первые запросы уйдут
мимо моков), а чанк с моками весит заметно больше остальных. Чтобы это окно не выглядело
пустым белым экраном, в `index.html` лежит статичная заглушка со скелетоном карточек —
она видна с первого кадра, знает про тёмную тему и удаляется после первого рендера React.

**Состояния запросов.** Список и деталка грузятся через TanStack Query со скелетонами,
empty- и error-состояниями. Prefetch детальной страницы — по `onMouseEnter`/`onFocus`
на карточке (`queryClient.prefetchQuery`) плюс `preload="intent"` у ссылок. Ретраи
только для сетевых и 5xx; 4xx не повторяются.

**Разделение бандла.** Каждая страница — отдельный чанк (`lazy` + `Suspense` в корневом
layout), моки с генератором данных тоже уезжают в свой чанк через динамический импорт
в `main.tsx`. Основной бандл ~290 кБ вместо одного файла на 1,1 МБ; `preload: 'intent'`
подтягивает код страницы заранее, по наведению на ссылку.

**Обратный отсчёт.** `getTimeLeft` — чистая функция (текущее время приходит параметром),
поверх неё хук `useTimeLeft` с тиком раз в секунду, который останавливается по истечении.
На карточке и деталке идущих торгов виден остаток времени, а `getPrimaryAction` получает
`isExpired` и гасит ставку сразу, не дожидаясь, пока сервер обновит `can_set_bet`.

**История ставок — журнал, а не текущее состояние.** Изменение ставки добавляет новую
запись, а не переписывает прежнюю: у `BetItem` есть `created_at`, `is_rejected` и
`cancel_reason`, а у `GET /bets` — параметр `all` («в том числе отменённые»), то есть схема
описывает именно журнал. ТЗ это подтверждает, требуя «количество участников» отдельным
пунктом от «списка ставок»: участники считаются по уникальным организациям, а не по числу
строк. Чтобы прошлые ставки не выглядели действующими, ViewModel помечает их
`isSuperseded` (по месту от сервера, а при `hide_places` — по времени) и таблица показывает
статус «Неактуальна».

**Темы.** Светлая и тёмная палитры описаны токенами в `app/styles/index.css`; переключает
их единственный класс `dark` на `<html>`, поэтому `dark:`-классов в компонентах нет.
В шапке — группа из трёх кнопок с подписью «Тема»: «как в системе», «светлая», «тёмная»;
активная подсвечена, нужная выбирается одним нажатием. Выбор хранится в localStorage, а маленький скрипт в `index.html` применяет тему до первого кадра — иначе
при перезагрузке в тёмной теме экран мигает белым. `color-scheme` переключается вместе с
палитрой, поэтому нативные календари в фильтрах и скроллбары тоже темнеют.

**Валюта.** Суммы форматируются по `payment.currency_code` (числовой ISO 4217 из DTO):
`currencyFromCode` переводит `643 → RUB`, незнакомый код падает на рубли, а не печатает
сырое число. Код валюты доезжает до карточки, деталки, формы ставки и таблицы ставок
через ViewModel.

**Ограничения из DTO** показываются явно, а не молчаливым скрытием: `can_set_bet`,
`hide_bets_history` (запрос ставок при нём не отправляется вовсе),
`hide_points_address_and_contacts`, `no_view_cargo_price`, `hide_places`.
На детальной странице есть блок «Ограничения аукциона» со всеми флагами — чтобы
проверяющему было видно, что именно влияет на UI.

### Осознанные компромиссы

Четыре решения, которые выглядят как отступления от привычных правил, но приняты намеренно.

**`shared/ui` без публичного API.** У всех слайсов есть `index.ts`, а у `shared/ui` — нет:
компоненты импортируются по прямым путям (`@/shared/ui/button.component`). Баррель на два
десятка компонентов тянул бы в бандл всё сразу и провоцировал циклы между `ui` и `lib`.
Прямые импорты здесь дешевле и честнее — это же соглашение у shadcn/ui, откуда взят подход.

**ViewModel хранят готовые подписи.** `statusLabel`, `aucTypeLabel`, `measurementLabel` —
это уже русский текст, а не ключи. Так компоненты остаются без словарей и логики выбора
подписи, а маппинг enum → текст покрывается обычными тестами. Плата — при появлении i18n
подписи придётся заменить на ключи и переводить в компонентах; для одноязычного приложения
эта цена не оправдана заранее.

**`CURRENT_USER` в `shared/config`.** По-хорошему текущий пользователь — это сущность
(`entities/viewer`) с загрузкой профиля. Но в схеме нет ни `securitySchemes`, ни эндпоинта
профиля: «пользователь» существует только как организация, от которой считается «моя
ставка». Заводить ради константы сущность со слоем API — усложнение без выигрыша.

**Стор панели фильтров живёт в фиче, а не в виджете.** `useFiltersPanelStore` хранит
состояние «выезжающая панель открыта» — по букве это UI-состояние виджета. Но открывает
панель кнопка из тулбара, а закрывает форма после «Применить»: это два разных компонента,
и стор в фиче — их общая точка. Перенос в виджет добавил бы связность, не убрав ничего.

## Как проверял

Автоматически — `npm run test`: 266 тестов, 14 файлов.

- **Контракт схемы** (`contracts.contract.test.ts`) — поля, enum'ы, nullable для 42 DTO.
- **Search params** — дефолты, мусорные значения, чужие query-параметры, города вне
  словаря, даты в неверном формате, числовой `cargo_num` из URL.
- **Request builder** — коды статусов, ISO-даты со смещением, сортировка, отсечение
  пустых фильтров; итоговое тело валидируется схемой `AuctionListRequest`.
- **VM-мапперы** — nullable-поля, отсутствующие блоки `price`/`your`, скрытые контакты
  и цена груза, `car = null`, схлопывание незнакомого статуса в `Unknown`.
- **Правила ставки** — все четыре типа аукциона, шаг, границы, дробные значения,
  вывод ставки НДС из пары цен DTO.
- **Обратный отсчёт** — остаток, истечение, срочность, битые и пустые даты.
- **Темы** — разворачивание системного предпочтения, подписи вариантов, класс на `<html>`.
- **ViewModel ставок** — участники по организациям, пометка перекрытых ставок, отменённые
  вне подсчётов.
- **Чипсы фильтров** — подписи, снятие одного значения из массива, сброс страницы.
- **Сортировка ставок** — по месту / цене / времени, ставки без места всегда внизу.
- **MSW-стор** — фильтры, пагинация, сортировка, отменённые ставки, пересчёт мест,
  влияние ставки на список.
- **ViewModel ставок** — участники по организациям, пометка перекрытых ставок при видимом
  и скрытом рейтинге, отменённые ставки вне подсчётов.
- **Интеграция (RTL + MSW)** — skeleton / error / empty списка, пагинация, переход в
  деталку, открытие формы ставки по прямой ссылке, отказ при нарушении правил торгов,
  успешная ставка (проверяется и UI, состояние стора, и success-toast), `can_set_bet = false`,
  скрытая история ставок, 404.

Ручной чек-лист (тот же набор, что покрыт тестами, но в браузере):

1. Фильтры развёрнуты сразу → «Применить»: условия уходят в URL, страница сбрасывается
   на первую. Прокрутите список вниз — строка сортировки прилипает под шапкой и в ней
   появляется кнопка «Фильтры»: та же форма открывается выезжающей панелью,
   возвращаться к началу страницы не нужно.
2. Пагинация и смена размера страницы; «назад/вперёд» в браузере восстанавливают фильтры.
3. Ручная правка search params (`?page=abc&statuses=НЛО`) — страница живёт, значения падают в дефолты.
4. Наведение на карточку → в Network виден prefetch `GET /auctions/{uuid}`, переход мгновенный.
5. Деталка → вкладка «Ставки» → переключатель «Показывать отменённые», сортировка
   кликом по заголовкам «Место», «Цена с НДС», «Время». После изменения своей ставки
   прошлая остаётся в журнале со статусом «Неактуальна».
6. Ставка: кнопки «−шаг» / «+шаг», превью суммы без НДС под полем; цена вне шага или
   направления даёт ошибку до отправки; корректная — тост, закрытие модалки, обновлённая
   цена в деталке и в списке.
7. Чипсы применённых фильтров над списком: каждый снимается крестиком.
8. Переключатель темы в шапке: три варианта, активный подсвечен, выбор переживает
   перезагрузку без вспышки белого.
9. Прямые ссылки из таблицы ниже, включая `/auctions/{uuid}/bet`.
10. Ширины экрана 360 / 768 / 1440: фильтры сворачиваются в кнопку, таблица ставок
    превращается в карточки, модалка ставки становится полноэкранной.

## Расхождения в самой схеме и как они решены

1. **`status_mobile` в списке уже, чем в деталке.** `AuctionListItemTrading.status_mobile`
   объявляет 6 значений, `TradingStatus` — 9. Контракт воспроизведён как есть: в списке
   значения вне узкого набора схлопываются в `Unknown` (см. аукцион №9 в таблице выше).
2. **`auc_type` в фильтре не принимает `Unknown`**, хотя в ответе такое значение легально.
   В UI фильтра `Unknown` не предлагается.
3. **`hide_bets_history` объявлен дважды** — в `AuctionShowResponse` и в
   `AuctionShowTrading`. История скрывается, если флаг взведён хотя бы в одном месте.
4. **Шага ставки нет в списочном DTO.** `AuctionListItemTradingPrice` — это только
   `start`/`current`/`current_no_vat`. ТЗ требует шаг на карточке, поэтому поле там есть,
   но показывает «— в деталях» с пояснением в подсказке: выдумывать значение нельзя,
   а реальное приходит в детальном DTO (видно на карточке аукциона и в форме ставки).
   Четвёртой метрикой рядом показана стартовая цена — она в списочном контракте есть.
5. **Противоречивые примеры НДС.** В примерах схемы `current_no_vat` посчитан от 1.22,
   а `start_no_vat` / `min_no_vat` / `step_no_vat` — от 1.2. Мок использует ставку 20 %
   везде (она же указана в `AdmittedOrganization.current_vat_rate`).
6. **`your.last_bet` в списке против `last_bet` + `last_bet_with_vat` в деталке.**
   По значению из примера (30000) списочное поле трактуется как цена с НДС; в деталке
   `last_bet` — без НДС, `last_bet_with_vat` — с НДС.
7. **Тело успешного `POST /bets` не типизировано** («проксируется от upstream»).
   Мок возвращает созданный `BetItem`, клиент на тело не опирается — только
   инвалидирует list / detail / bets.
8. **Поля с `example: null` без флага `nullable`** (например `AuctionListItemPayment.consignor`).
   Такие поля считаются nullable — иначе валидный ответ upstream не прошёл бы разбор.
   Правило зафиксировано в `shared/api/contracts/common.ts` и проверяется contract-тестом.

## Ограничения

- Авторизации нет: в схеме отсутствуют `securitySchemes`, Bearer-токен не отправляется.
  «Текущий пользователь» зашит в `shared/config/env.ts` (ООО Перевозчик, id 14).
- Данные живут в памяти вкладки и сбрасываются при перезагрузке: MSW пересобирает сид
  при каждом старте. ТЗ требует, чтобы моки меняли состояние после мутаций (это выполнено
  и покрыто тестами), персистентность между сессиями в задании не оговорена. Чтобы
  ограничение не выглядело потерей данных, оно повторяется в success-тосте после ставки.
- Из фильтров реализован минимум по заданию плюс сортировка и размер страницы; остальные
  поля `AuctionListRequest` (вес, объём, тип кузова, заказчик, радиусы городов) типизированы
  и поддержаны моком, но в UI не вынесены.
- Списочный запрос не отменяет предыдущий вручную — этим управляет TanStack Query.
- MSW попадает в production-бандл: это демо, где моки и есть бэкенд. Он вынесен в
  отдельный чанк, но грузится на старте — иначе приложению не с чем работать.
- Не реализованы: избранное, чат, встречные ставки, отзыв ставки, бесконечный скролл, i18n.
- Обратный отсчёт идёт по часам клиента: мок не проверяет время на «сервере», поэтому
  ставка в истёкшем аукционе блокируется только в UI.
